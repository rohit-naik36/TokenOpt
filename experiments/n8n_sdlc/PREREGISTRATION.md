# Pre-registration: n8n SDLC workflow benchmark (output discipline x structured handoff)

Status: **PRE-REGISTRATION, committed before any full run.** Only the 1-ticket x 4-arm x 1-rep pilot (section 9) has been run. Anything that changes after the first full-run row is recorded in a Deviations section of the report, never edited here. Branch `feat/n8n-workflow-benchmark`. Nothing in this directory is pushed.

## 1. Question
In a five-stage SDLC workflow run by n8n against a local 9B model, do (A) a verbatim output-discipline instruction and (H) passing each stage only the structured fields it needs reduce tokens and weighted cost versus naive chaining, without losing deterministic quality? This tests two levers on one local model and one synthetic workload. It does not transfer to Claude models, to other workflows, or to real tickets.

## 2. System under test
- **Workflow** (`workflow.json`, generated by `build_workflow.py` from the frozen files in `prompts/`): Webhook -> 5 HTTP Request nodes (`triage`, `requirements`, `plan`, `review`, `release_note`; each `POST {ollama_base_url}/api/chat`, `stream:false`, `think:false`) -> `collect` Code node returning, per stage, `prompt_eval_count`, `eval_count`, `turns` (= 1), `output`, `total_duration`, `done_reason`. Arm, model, Ollama base URL, temperature, seed, ticket and diff are webhook inputs. Deviation from the literal brief: none in topology; prompt composition is done inside each HTTP node's body expression, not in extra nodes.
- **Stage outputs** are JSON objects; each system prompt (role, context, input, output format, constraints) is in `prompts/<stage>.txt` and is identical in every arm.
- **Infrastructure** (recorded 2026-10-14): n8n 2.43.5, image `n8nio/n8n:latest` = `sha256:4fc4c67bf5fb990201a71d94c7070abf8dd0619cb8af1d059877a447f3640392`, container `--memory 1500m`, named volume `n8n_sdlc_data`, port 5678, `EXECUTIONS_DATA_SAVE_ON_SUCCESS=none`; Ollama 0.35.0 reached from the container at `host.docker.internal:11434`; model `qwen3.5:9b`, digest `6488c96fa5faab64bb65cbd30d4289e20e6130ef535a93ef9a49f42eda893ea7`. Options: `temperature 0.3`, `seed = rep number` (same seed for every arm of a given ticket and rep), `num_ctx 12288`, `num_predict 2048`, `think false`. The runner unloads the model before every run, so every stage's `prompt_eval_count` is the full prompt (no KV-cache reuse across runs or stages) and there is no cached-token term.

## 3. Arms (one change per arm; texts frozen in files)
| arm | what the stage receives | system prompt |
|---|---|---|
| **control** | naive chaining: the full ticket (all fields) plus the raw text of every upstream stage output; the review stage also gets the diff | stage prompt |
| **A** | same user content as control | stage prompt + `\n\n` + `prompts/arm_A.txt` |
| **H** | only the fields the stage needs, as a JSON object built from the parsed upstream JSON (field lists in `build_workflow.py`, function `needed`) | stage prompt |
| **AH** | H's user content | stage prompt + arm A text |

`prompts/arm_A.txt` is byte-identical to the arm-A text in `docs/EXPERIMENT_OUTPUT_TURN_LEVERS.md` of the otl-001 experiment (verified by substring match). That text was written for a coding agent that edits files ("make edits as the smallest possible diffs ... reply with one line") and applies only loosely to JSON-producing stages; this is a stated limitation, not edited. Upstream parsing for H tolerates a markdown fence and a missing closing `]`/`}`; if parsing still fails the stage receives `{"unparsed_upstream": <first 1500 chars>}`. Arms are interleaved per ticket and rep in the order control, A, H, AH.

## 4. Inputs and ground truth
- 8 tickets (`tickets/T01..T08.json`; mixed bugs, features, security, chore; Python and TypeScript), each with a ticket body, comments and a 18-43 line diff. Exactly one defect is planted per diff and recorded in `tickets/ground_truth.json`, which only `score.py` reads (never the workflow or runner). Defects: T01 offset off-by-one, T02 retry on 4xx, T03 TTL reset on every request, T04 unescaped embedded quotes, T05 inverted expiry check, T06 SQL injection, T07 cache key omits currency, T08 UTC relabelled as local time.
- The planted defect is real but the diffs were written by the experimenter; whether a given diff contains additional, unplanted problems is not controlled (a reviewer finding one counts as an `other_finding`, never as a hit).

## 5. Endpoints
All token counts are the Ollama-reported `prompt_eval_count` and `eval_count`, summed over the five stages of a run.
- **Co-primary, per arm vs control:** output tokens, total tokens (prompt + output), and weighted cost **W = prompt + 4 x output** (uncached 1, output 4; there is no cached term, see section 2). Sensitivity: output weight 1 and 8. Headline = W.
- **Secondary:** per-stage tokens, wall time per run, `done_reason = length` count, the blind judge score, `other_findings`, repaired-brace variants.
- Each is reported as the ratio arm/control of means over paired (ticket, rep) units, with a **paired percentile bootstrap 95% CI** (resample units, 10,000 resamples, seed 20261015), as implemented in `score.py`. No p-values are used for the decision; the CI is the headline.

## 6. Quality checks (deterministic, primary) and gate
Defined and implemented in `score.py` before any full run; the defect match rule is written in its docstring and fixed. In brief: each stage output must parse as one JSON object (fence tolerated), have the required keys/types/enums, list lengths in the stated range (acceptance criteria 3-6, plan steps 3-7, review findings <= 6, release-note changes 1-4, release-note summary <= 60 words) and not be truncated (`done_reason != length`); the review must contain a finding in the planted file whose issue/fix text matches one of the ticket's regexes.
- **Quality gate:** an arm passes if, versus the control, **both** its format rate (every stage ok) and its defect-hit rate are >= 95% of the control's. If the control's format rate is below 0.5 the format component is declared uninformative in advance and only defect-hit is used (see the pilot finding in section 9). The composite (all stages ok and defect hit) is reported but is not the gate.
- With n = 40 units per arm a gate "pass" means "not distinguishable at this n", not equivalence; Wilson intervals are reported.
- **Secondary, blind judge:** `export_blind.py` writes anonymized packets (ticket, diff, five stage outputs; no arm, run id or rep) with the id-to-run map in a separate file; scored with `judge_rubric.md` (four criteria, total 10), as in otl-001. The judge is Claude run inside Claude Code (no API key), temperature not controllable, so scores are non-deterministic; scores are written to a file before the map is opened; mean >= 95% of control is reported as a secondary gate and never merged with the deterministic gate. Blinding is imperfect (terse A/AH outputs and structured H handoffs may be recognizable).

## 7. Sample size
**8 tickets x 5 reps (seeds 1-5) x 4 arms = 160 runs; 40 paired units per arm.** The pilot took 39-58 s per run (mean about 45 s, model reload included), so the full run is about 2 to 2.5 hours. Variance is not known: the pilot is one unit. The minimum detectable effect will be computed from the observed paired spread and reported with the results; with 8 distinct tickets, effects are conditional on this ticket set (reps of one ticket are correlated even with different seeds), so the 40 units are not 40 independent samples of "tickets in general". Harness errors (HTTP/transport/Ollama/malformed response) are recorded separately, not counted as quality failures, retried once on the next invocation, and at most 2 attempts are made per run; more than 8 unrecoverable harness errors stops the experiment.

## 8. Decision rules (fixed now)
For each arm and for each of output tokens, total tokens, W:
- **Reduction shown:** the 95% CI of the ratio lies entirely below 1.
- **Increase shown:** entirely above 1.
- **No material effect:** the CI lies entirely inside [0.90, 1.10].
- **Inconclusive:** otherwise (including a CI that contains 1 and extends beyond 0.90 or 1.10). Inconclusive is not "no effect".
- An arm's cost result counts as **promising only if the quality gate passes** (section 6). A reduction with a failed gate is reported as a quality-cost trade-off. A reduction in tokens with `done_reason = length` truncations driving it is reported as such.
- Three endpoints x three arms are reported, none corrected for multiplicity; the claim "an effect exists" is only made where the CI for W excludes 1 and the output-token and total-token CIs agree in direction.

## 9. Pilot (1 ticket T01 x 4 arms x 1 rep; not part of the experiment, not in the analysis)
Run by the experimenter through `runner.py`; `pilot_v1_*` is the first pilot (temperature 0, seed 7, parser without brace repair); `pilot_*` and `pilot_summary.txt` is the pilot with the final workflow. Both are n = 1 per arm and say nothing about effects.
- Mean prompt / output tokens per stage and wall time: see `pilot_summary.txt`. Pilot totals (prompt + output): control 8817, A 7473, H 4744, AH 4774; wall 58 / 43 / 40 / 39 s; all four runs completed with zero harness errors.
- **Finding that shaped this document:** in both pilots the `plan` stage failed the strict JSON check in all four arms because the 9B model omitted the final closing brace; one `review` output in pilot 1 (arm H) had the same defect, and the H release-note stage then received the unparsed-upstream fallback because the pre-repair parser could not read it. Parsing the upstream output with brace repair (section 3) was added to the workflow before the second pilot. Strict scoring was kept, a repaired variant is reported alongside, and the format-gate rule in section 6 was written in response. **Open decision for the owner before the full run:** whether to enforce JSON syntax with Ollama's `format` option (every arm; this would make the format check uninformative for syntax but would not affect the other checks) or to run as registered here. Running as registered is the default.
- Temperature 0 with a fixed seed makes repeated runs identical, so reps would not be independent; the final workflow takes `temperature` (default 0.3) and `seed` (= rep) as inputs.

## 10. Limitations stated in advance
Local 9B model only; synthetic tickets and diffs written by the experimenter, 8 of them; one planted defect each, so defect-hit has coarse resolution per ticket; regex-based match rule can over- or under-count; arm A text is a coding-agent instruction applied to JSON stages; H changes the formatting of the input as well as its content; no length-matched placebo; control and H differ in what the model sees, so quality differences cannot be attributed to token count alone; wall time includes model reload; judge is a single non-deterministic Claude Code pass.

## Amendment 1 (2026-10-14, before any full-run data exists)
1. **Plan-stage check, no workflow change.** Evidence from all 8 pilot plan calls (`pilot_v1_runs.jsonl`, `pilot_runs.jsonl`): `done_reason = stop` in 8/8; `eval_count` 349-537 against `num_predict` 2048 (at most 26% of the cap); every output ends at `...]` with the final `}` missing, so the failure is the model closing the object early, not truncation. Thinking tokens: with `think:false` the response `message` has no `thinking` field (direct Ollama probe, 9 completion tokens for a 12-character reply); with `think:true` the same model returns `message.thinking` and counts it in `eval_count` (probe: 719 thinking characters, empty content, `done_reason = length` at a 300-token cap). The workflow sends `think:false` in every arm, so reported counts are content tokens only. Neither truncation nor thinking inflation is the cause, so `num_predict`, `think` and the workflow are unchanged, and no pilot was re-run. The open `format: json` decision in section 9 stands.
2. **Bootstrap clusters on tickets.** The confidence intervals in section 5 resample **tickets** (with replacement) and keep all reps of each drawn ticket; the ratio is sum(arm)/sum(control) over the resampled paired units (`score.py`, 10,000 resamples, seed 20261015). This replaces "resample units" in section 5, which treated the 5 reps of a ticket as independent. With only 8 clusters the percentile interval is coarse and likely too narrow; read it as indicative. The Wilson intervals in section 6 still treat runs as independent and are approximate for the same reason.
