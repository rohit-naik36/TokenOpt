# Stage 2 pre-registration: n8n SDLC workflow on the Claude Messages API

Status: **pre-registration, committed before any Anthropic API call.** Only the 1-ticket x 4-arm x 1-rep pilot (section 11) is authorised now. The full run starts only after the owner reconciles the pilot against the Console and sets the full-run cap (section 9). Anything changed after the first Stage 2 call is recorded in a Deviations section of the report, never edited here. Branch `feat/stage2-claude-api` (from `feat/n8n-workflow-benchmark`). Nothing is pushed.

Stage 1 (`PREREGISTRATION.md`, `REPORT.md`) is the local-model experiment. This document inherits its question, arms, quality checks and CI method, and lists every deviation in section 12.

## 1. Question
Do the Stage 1 levers still matter when the SDLC chain runs on a Claude model? Arms and quality checks are as in Stage 1: (A) a verbatim output-discipline instruction, (H) passing each stage only the structured fields it needs, (AH) both, against naive chaining (control). Endpoints: output tokens, total tokens, census-weighted cost W and dollar cost, with and without prompt caching. This tests one model (`claude-haiku-5-5`), one synthetic workload and eight tickets. It does not transfer to other Claude models or to real tickets.

## 2. Model and endpoint
- **Model:** `claude-haiku-5-5` (exact ID; no date suffix). Default per owner brief.
- **Endpoint:** `POST https://api.anthropic.com/v1/messages`, headers `x-api-key` (from the n8n container environment, `$env.ANTHROPIC_API_KEY`; never in the payload, workflow JSON or logs), `anthropic-version: 2023-06-01`, `content-type: application/json`. Raw HTTP from n8n HTTP Request nodes; no SDK.
- **Request shape per stage:** `model`, `max_tokens: 2048`, `system` (one text block: the frozen stage prompt, plus the arm-A text in arms A and AH), `messages` (one user turn: the naive or H-style user content, as in Stage 1), `thinking: {type: "disabled"}`. Haiku 5.5 runs adaptive thinking when `thinking` is omitted, so it is set explicitly to match Stage 1 (`think: false`).
- **Not sent:** `temperature`, `top_p`, `top_k` (Haiku 5.5 accepts only the default temperature 1 and default top_p 0.99; any other value is a 400), and any seed (the Messages API has no seed parameter). The `output_config.effort` field is not sent, so the Haiku 5.5 default (`medium`) applies to every arm and phase.
- **Workflow:** `workflow_stage2.json` (generated by `build_workflow_stage2.py`), five HTTP Request nodes, one per stage, guarded by `guard_<stage>` Code nodes that stamp stage start times and route failures. Stage 1 `workflow.json` is unchanged.

## 3. Arms (unchanged from Stage 1, texts frozen in `prompts/`)
| arm | what the stage receives |
|---|---|
| control | naive chaining: full ticket plus raw text of every upstream stage output; review also gets the diff |
| A | control user content; system = stage prompt + `prompts/arm_A.txt` |
| H | only the fields `needed()` lists, as JSON built from parsed upstream output (unchanged from Stage 1) |
| AH | H user content; system = stage prompt + arm-A text |

Arms interleave per ticket and rep in the order control, A, H, AH.

## 4. Caching phases
- **Phase A (none):** no `cache_control` anywhere. Used by the pilot and the first full-run phase.
- **Phase B (fixed policy, same for every arm):** `cache_control: {type: "ephemeral"}` (default 5-minute TTL) on the single `system` text block of every stage call. Nothing else is marked. The system block is identical across reps and tickets for a given stage and arm, so the cacheable prefix is stable; the user content (ticket, upstream outputs, diff) sits after it and is never cached. Haiku 5.5 minimum cacheable prefix is 512 tokens (claude-api skill, `shared/prompt-caching.md`); a stage system prompt shorter than that silently does not cache, and the report must show `cache_creation_input_tokens` per stage to confirm the policy took effect.
- Phase B is not run until the owner has filled the cache write and cache read prices (section 8), and the pilot's phase-A numbers have been reconciled.

## 5. Tickets, reps and sample size
- **Tickets:** the same eight tickets as Stage 1 (`tickets/T01..T08.json`), ground truth in `tickets/ground_truth.json`, read only by `score.py`.
- **Reps:** 5 per ticket (`--reps 5`). Stage 1 reps were seeded (seed = rep). Stage 2 reps are **independent samples** because no seed exists and temperature is fixed at 1. Rep index is recorded but carries no seed meaning.
- **Runs:** 8 tickets x 5 reps x 4 arms = 160 runs per caching phase; 40 paired units per arm; each run is five stage calls. Two phases means 320 runs and 1,600 calls in the full experiment.

## 6. Endpoints (fixed now)
Per run, summed over the five stages (all counts from the provider `usage` object of each call):
- **Co-primary:** output tokens; total tokens (`input_tokens + cache_creation_input_tokens + cache_read_input_tokens + output_tokens`); census-weighted cost **W**; dollar cost (section 8).
- **W definition (from tokenopt census, `experiments/sdlc_census/census.py` on `feat/workflow-optimizer`):** `W = (input + cache_creation) * 1 + cache_read * 0.1 + output * 4`. The census module has no cache-write term, so cache-creation tokens are weighted 1. **This understates cache-write cost in W; the dollar figure prices cache writes once the prices file has them.** `tokenopt.census` does not exist on this branch (checked: no `census` module in any tracked file of this branch); the census file that reads per-call usage lives on `feat/workflow-optimizer`, reads OpenCode session logs, and is not imported here. `stage2_cost.census_turns()` is the adapter that presents each Stage 2 call as a census turn `(prompt, cached, completion)` without changing what a turn is (one provider call).
- **Ratio:** arm / control of means over paired (ticket, rep) units; **paired ticket-cluster percentile bootstrap 95% CI** (resample tickets with replacement, keep all reps of a drawn ticket; 10,000 resamples; seed 20261015), the Stage 1 amendment-2 method. With 8 clusters the interval is coarse; read it as indicative.
- **Secondary:** per-stage tokens; `stop_reason = max_tokens` count (truncation, the Stage 1 `done_reason = length` analogue); latency per stage (n8n guard stamps, an upper bound that includes n8n overhead); retries and billed failed attempts (section 7); API judge score (section 9); defect hits and other findings.
- Sensitivity: output weight 1 and 8 for W.

## 7. Harness errors and retries
- A webhook run either completes (all five stages HTTP 200) or fails at a stage. A failing stage returns `sdlc_failure` with `http_status`, `error_type`, `request_id` and `retry-after`. Completed earlier stages of that attempt are billed and are logged as `call` rows with that attempt number, so the dollar total includes them.
- **Backoff:** on HTTP 429, 529 or 5xx the runner waits `retry-after` seconds when the header is present (capped at 600 s), otherwise `min(20 * 2^(attempt-1), 300)` s plus 0-5 s jitter, then retries the whole run. Each attempt is logged (`attempt_error` row). Max 4 attempts per run.
- **Transport errors and timeouts** (no `sdlc_failure`) are logged with `usage_known: false`. The API may have billed a partial run that the runner cannot see; the report counts these runs separately and states the count. More than 8 such errors stops the experiment.
- A run that exhausts its attempts is `harness_error`, is not scored as a quality failure, and is retried on the next invocation.

## 8. Prices and dollar cost
- `stage2_prices.json` holds USD per 1,000,000 tokens. Haiku 5.5 input 0.10 and output 0.50 are copied from the claude-api skill model table (cached 2026-10-06, first-party, prompts up to 100K tokens); Sonnet 4.6 input 3.00 and output 15.00 likewise. **Cache write and cache read prices are `TODO` for both models** and are not invented. The owner reviews every value against the Console before any run is treated as final.
- Dollar cost per call = input x price_in + output x price_out + cache_creation x price_write + cache_read x price_read. A call with a non-zero count in an unpriced unit has `cost_usd: null`; the runner refuses to start a caching phase whose prices are not all numeric.

## 9. Spend caps, budget guard and judge
- **Pilot cap: $0.50.** The runner aborts before any run whose estimated cost (the maximum run cost seen so far, or a worst-case bound of 5 x (20,000 input + 2,048 output) tokens before the first run finishes) would take spending past the cap, and aborts after any run that does. The cap is passed as `--cap-usd`. One run can overshoot by at most one run's cost; the guard is a stop rule, not an exact limit.
- **Full-run cap:** not set by this document. The owner sets it after reconciling the pilot. Experimenter's suggestion: $5.00 for both phases, about 100 times the expected cost, to be confirmed or changed by the owner before the run starts.
- **API judge (secondary, not in the gate):** model `claude-sonnet-4-6`, temperature 0 (accepted on this model), blind. Packets contain ticket, diff and the five stage outputs in full, with no arm, run ID or rep (`export_blind.py` logic). Rubric `judge_rubric.md` (four criteria, total 10). Scores are written to a file before the id-to-run map is opened. Mean >= 95% of control is reported as a secondary gate and never merged with the deterministic gate. Blinding is imperfect: terse A/AH outputs and structured H handoffs may be recognisable.

## 10. Quality gate and decision rules (as in Stage 1)
- **Quality gate (deterministic, primary):** an arm passes if its format rate (every stage parses, has the required keys and ranges, is not `max_tokens`-truncated) and its defect-hit rate are each >= 95% of control's. Checks are `score.py` as in Stage 1, unchanged. Format rate is declared uninformative if control's is below 0.5.
- **Cost decision rules:** for each arm and each of output tokens, total tokens, W and dollars: reduction shown if the 95% CI of the ratio lies entirely below 1; increase shown if entirely above 1; no material effect if entirely inside [0.90, 1.10]; otherwise inconclusive. A reduction counts as promising only if the quality gate passes.
- **Transfer rule:** a Stage 1 finding (local qwen3.5:9b) is said to **transfer to claude-haiku-5-5** only if, in Stage 2 phase A, the same arm shows the same direction of effect on W with the CI excluding 1 and the quality gate passing. A Stage 1 finding whose Stage 2 CI includes 1 is reported as not transferred, whatever the point estimate. Phase B (caching) is judged on its own against phase A, not against Stage 1.
- No p-values are used for the decision. Three endpoints x three arms are reported, none corrected for multiplicity.

## 12. Deviations from Stage 1
1. **Model and backend:** Claude Haiku 5.5 via the Messages API, not qwen3.5:9b via Ollama. The Ollama branch is kept in the workflow and was smoke-tested in this stage (one control run) to confirm it still works.
2. **Sampling:** temperature is not set (Haiku 5.5 requires the default). Stage 1 used temperature 0.3 and seed = rep. Stage 2 reps are independent samples (section 5).
3. **Thinking:** explicitly disabled (`thinking: {type: "disabled"}`) to match Stage 1's `think: false`; omitting the field would enable adaptive thinking on this model.
4. **Output cap:** `max_tokens` 2048, equal to Stage 1's `num_predict`. `stop_reason = max_tokens` replaces `done_reason = length`.
5. **Token counting:** provider `usage` fields replace Ollama's `prompt_eval_count` / `eval_count`. Stage 2 `prompt_tokens` include cache creation and read; Stage 1 had no cache term.
6. **Cost:** dollars added (section 8); census weight W kept, with the cache-write weighting noted in section 6.
7. **Judge:** API `claude-sonnet-4-6` at temperature 0, replacing the Claude Code judge (which had no API key). Same rubric, same blinding idea, full packets.
8. **Retries:** whole-run retries with logged, billed partial stages (section 7). Stage 1 retried only transport/harness errors, without backoff.
9. **Latency:** per-stage latency comes from n8n guard timestamps and includes n8n overhead.
10. **Infrastructure:** n8n container recreated with `N8N_BLOCK_ENV_ACCESS_IN_NODE=false`, `EXECUTIONS_DATA_SAVE_ON_ERROR=none` and the API key in its environment. Image digest and Ollama/model digests are as in Stage 1 section 2 for the Ollama branch; the Anthropic branch has no local model.
11. **Census module:** the `tokenopt.census` named in the brief does not exist on this branch. Stage 2 uses the census weights and turn definition with an adapter (`stage2_cost.py`) and does not import the census module.

## 13. Limitations stated in advance
Single model; synthetic tickets written by the experimenter; eight tickets (cluster bootstrap is coarse); one planted defect per diff; regex defect matching; arm A is a coding-agent instruction applied to JSON stages; H changes input formatting as well as content; no length-matched placebo; prompt caching in phase B depends on the 512-token minimum being met by each stage prefix; cache prices unknown until the owner fills them; the API judge is a single temperature-0 pass per packet and blinding is imperfect; pilot n = 1.

## 15. Addendum: prep changes before phase A (2026-10-14, appended; sections 1-14 are not edited)
Made after the pilot's API calls and before any full-run call. Each change is a deviation from the text above.
1. **Prices (supersedes section 8's TODO):** `stage2_prices.json` now holds the Anthropic pricing page values checked 2026-10-14 for `claude-haiku-5-5`, `claude-sonnet-5-5` and `claude-sonnet-4-6`, including cache writes (5-minute and 1-hour) and cache reads. Haiku prompts over 100,000 input tokens are priced at a higher tier. The runner does not price them: `stage2_cost.dollars()` raises, the call is logged with `cost_usd` null and the run stops. Re-pricing the pilot's 20 calls gives $0.009173, unchanged (the pilot has no cache tokens and every request is under 4,120 input tokens).
2. **Webhook authentication (deviation from section 2's endpoint description):** the webhook requires header `X-Bench-Token`, compared in constant time with `$env.BENCH_WEBHOOK_TOKEN` in the n8n container (fail closed: an unset token rejects everything). A failed check returns HTTP 401 from a Respond node; no stage node runs, so no API call is made. The runner sends the header from `BENCH_WEBHOOK_TOKEN` in its own process and stops at once on 401 (no retry, nothing billed). The token is never written to a file.
3. **Runner key handling:** the runner no longer checks `ANTHROPIC_API_KEY` in its own process. The key is used only inside the n8n container.
4. **Spend cap:** `--cap` is an alias of `--cap-usd`. The runner stops before a webhook call whenever spend plus the next run's estimate would exceed the cap, which is at or before the cap being reached. It prints a running total every 20 stage calls.
5. **Workflow change:** `workflow_stage2.json` was regenerated. The Webhook responds through Respond nodes instead of the last node, so the n8n container must re-import and re-publish the workflow (section 14) before any run.
